# ooc-leaderrank

Многопоточная реализация LeaderRank для графов, которые не помещаются в RAM.
Рёбра хранятся на SSD в двумерной сетке блоков; в памяти остаются только
активные окна вершин и текущая порция рёбер.

Проект состоит из двух C++23-утилит:

- `lr-prepare` читает CSV/TSV, очищает граф и строит рабочий каталог;
- `lr-rank` вычисляет LeaderRank над подготовленным графом и записывает CSV.

Математика, выбор формата, контракты между компонентами и результаты проверки
описаны в [REPORT.md](REPORT.md).

## Quick Start

Команды ниже рассчитаны на чистую Ubuntu 22.04 и запускаются из корня
репозитория:

> **NB:** `lr-prepare` пересоздаёт указанный `<workdir>`, а `lr-rank`
> перезаписывает файл, переданный через `--out`.

```sh
./scripts/setup_ubuntu.sh
./scripts/build.sh lr-prepare lr-rank
build/native/src/prepare/lr-prepare examples/edges.csv ./workdir --budget 128M --threads 4
build/native/src/rank/lr-rank ./workdir --budget 128M --threads 4 --out ranks.csv
cat ranks.csv
```

Для графа из `examples/edges.csv` получится:

```csv
vertex,rank
1,0.297619047574699
2,0.273809523787349
3,0.261904761893675
4,0.166666666744277
```

## Как это работает

`lr-prepare` делит диапазон ID на $P$ интервалов и раскладывает рёбра по $P^2$
блокам `(src_interval, dst_interval)`. Утилита удаляет петли, сортирует каждый
блок по `(dst, src)` и схлопывает дубликаты.

На каждой итерации `lr-rank` обрабатывает сетку по столбцам. В RAM помещаются
один столбец назначений и одно окно источников; рёбра читаются из `blocks.bin`,
а два вектора рангов поочерёдно хранятся на диске. Сортировка по назначению
разводит потоки по непересекающимся диапазонам вершин, поэтому атомарные
операции не нужны.

Двумерная сетка позволяет не загружать граф или полный CSR в RAM, но требует
повторно читать окна рангов и степеней для каждого столбца.
Подробная оценка памяти и I/O приведена в
[разделе об эффективности](REPORT.md#оценка-ресурсов).

## Входные данные

`lr-prepare` читает CSV- и TSV-списки рёбер:

```text
from,to
1,2
2,3
```

Правила чтения:

- первые две колонки задают ориентированное ребро `from` $\to$ `to`;
- разделитель — запятая или табуляция, остальные колонки игнорируются;
- ID — целое число от `0` до `2 147 483 647`;
- первая содержательная строка может быть заголовком; рекомендуемый заголовок —
  ровно `from,to`;
- пустые строки, CRLF и строки-комментарии с `#` поддерживаются;
- кавычки и переносы строк внутри CSV-полей не поддерживаются;
- одна строка должна быть короче 256 KiB.

`lr-prepare` строит простой граф: удаляет петли и схлопывает дубликаты. Вершина
попадает в граф, только если встречается хотя бы в одном оставшемся ребре.
Изолированные вершины и вершины, представленные только петлями, в результат не
попадают.

Размер окон зависит от $R=\max(\mathrm{ID})+1$, а не только от числа разных ID.
`lr-prepare` отклоняет вход при $R>64M_0$, где $M_0$ — число рёбер до очистки,
и предлагает сначала плотно перенумеровать вершины.

Некоторые датасеты задают направление связи противоположно нужной семантике.
Флаг `--transpose` меняет `from` и `to` местами при подготовке.

## Командная строка

### Подготовка графа

```text
lr-prepare <edges> <workdir> --budget <size>
           [--threads <N>] [--transpose]
```

- `--budget` — бюджет рабочего набора, например `128M` или `2G`. Суффиксы
  `K`, `M`, `G` означают степени двойки;
- `--threads` — число рабочих потоков, по умолчанию `1`;
- `--transpose` — поменять направление всех рёбер.

`lr-prepare` читает вход дважды: первый проход определяет размер графа, второй
строит блоки. Между проходами файл нельзя изменять.

Значение `--threads` участвует в планировании памяти и сохраняется как
`threads_planned`. Это максимальное число потоков, с которым затем можно
запустить `lr-rank` над данным `<workdir>`.

### Вычисление рангов

```text
lr-rank <workdir> --budget <size> --out <ranks.csv>
        [--eps <E>] [--max-iters <N>] [--threads <N>]
```

- `--eps` — остановка при $L_1/N < \varepsilon$, по умолчанию `1e-9`;
- `--max-iters` — не более указанного числа итераций, по умолчанию `500`;
- `--threads` — по умолчанию значение из `<workdir>`; можно выбрать меньше, но
  нельзя больше;
- `--budget` — должен вмещать уже выбранную геометрию `<workdir>`. Используйте
  тот же или больший бюджет, что и на подготовке.

Если достигнут `--max-iters`, `lr-rank` записывает последнее приближение,
печатает `WARNING` в `stderr` и возвращает код `0`. В автоматическом запуске
проверяйте `converged=true`.

Обе программы поддерживают `--help`.

## Выходные данные

`lr-rank` создаёт CSV:

```text
vertex,rank
```

Строки отсортированы по возрастанию ID. Ground-узел в файл не попадает:
его стационарная масса равномерно распределяется между обычными вершинами,
после чего значения нормируются к сумме `1`. Числа печатаются с 15 значащими
цифрами.

## Сборка

Нужны Clang 18, libc++ 18, CMake, Ninja и POSIX threads. Исполняемые файлы не
имеют сторонних зависимостей во время запуска. При первой конфигурации CMake
скачивает зафиксированную версию GoogleTest `1.15.2`, поэтому в этот момент
нужен доступ к сети.

### Ubuntu 22.04

`setup_ubuntu.sh` устанавливает инструменты и создаёт `.venv` с
Python-библиотеками для генератора, эталонной реализации и графиков.
`build.sh` генерирует `build.ninja` через CMake, затем запускает Ninja. По
умолчанию используется каталог `build/native` и режим `Release`:

```sh
./scripts/setup_ubuntu.sh
./scripts/build.sh lr-prepare lr-rank
```

Каталог сборки и режим можно изменить через переменные окружения:

```sh
BUILD_DIR=build/debug BUILD_TYPE=Debug ./scripts/build.sh
```

Без списка целей `build.sh` также собирает тесты:

```sh
./scripts/build.sh
```

### Podman или Docker

```sh
podman build -f containers/Containerfile -t ooc-leaderrank-build .

podman run --rm -v "$PWD:/work" ooc-leaderrank-build \
  bash -ec 'BUILD_DIR=build/container ./scripts/build.sh'
```

Для Docker достаточно заменить `podman` на `docker`.

## Проверка

```sh
./scripts/build.sh lr-tests
ctest --test-dir build/native --output-on-failure
```

Команда запускает 93 unit-теста.

Для независимой численной проверки есть `scripts/reference_rank.py`: на
небольших графах он решает стационарную систему напрямую, на больших использует
SciPy.

```sh
.venv/bin/python scripts/reference_rank.py examples/edges.csv --out /tmp/reference.csv
```

Для запуска под жёстким лимитом памяти используйте `run_capped.sh`:

```sh
# Linux
scripts/run_capped.sh 128m build/native/src/rank/lr-rank ./workdir --budget 128M --threads 4 --out ranks.csv

# macOS, после контейнерной сборки из предыдущего раздела
scripts/run_capped.sh 128m build/container/src/rank/lr-rank ./workdir --budget 128M --threads 4 --out ranks.csv
```

На Linux скрипт использует cgroup v2 через `systemd-run`; на macOS — лимит
контейнера Podman. Воспроизводимые результаты большой проверки приведены в
[REPORT.md](REPORT.md#проверка-результатов).

## Датасеты и бенчмарк

Генератор принимает `--seed` и умеет добавлять гиперузлы:

```sh
mkdir -p data/raw
.venv/bin/python scripts/gen_synthetic.py \
  --vertices 2000000 \
  --avg-degree 12 \
  --hypernodes 3:50000 \
  --seed 42 \
  --out data/raw/synthetic.csv
```

Для сравнения числа потоков:

```sh
BUILD_DIR=build/native BUDGET=128M \
  scripts/bench_threads.sh synthetic=data/raw/synthetic.csv
```

Скрипт запускает `1, 2, 4, 8` потоков по три раза, сохраняет сырой CSV и
проверяет, что `lr-rank` даёт одинаковый файл при $T=1$ и $T=8$.

Также доступны несколько открытых графов SNAP:

```sh
scripts/download_dataset.sh wikitalk
# варианты: lj, twitter, wikitalk, pokec
```

Перед ранжированием проверьте смысл направления ребра в описании конкретного
датасета.

## Ограничения

- `lr-rank` работает на одном узле и не распределяет граф между машинами.
- Один блок должен целиком помещаться в буфер сортировки. Если распределение
  рёбер слишком скошено, `lr-prepare` завершится с ошибкой. Внешней сортировки
  со слиянием пока нет.
- `--budget` ограничивает собственные буферы программы, но не задаёт системный
  лимит памяти. Стеки, накладные расходы аллокатора и файловый кэш учитывает ОС.
- `<workdir>` — внутренний кэш текущей версии, а не переносимый формат:
  в бинарных файлах нет номера версии, преобразования порядка байтов и
  контрольных сумм.
- `--eps` измеряет изменение двух соседних итераций и не задаёт универсальную
  границу расстояния до стационарного вектора.

Остальные границы применимости и отрицательные тесты разобраны в
[отчёте](REPORT.md#ограничения-и-непокрытые-случаи).
