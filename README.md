# ooc-leaderrank

Out-of-core LeaderRank для ориентированных графов, которые не помещаются в оперативную память.

## Что это

Две консольные утилиты на C++23, которые считают метрику LeaderRank для большого
ориентированного невзвешенного графа (например, 1 ГБ рёбер при лимите RAM 128 МБ),
включая графы с гипер-узлами — вершинами, чья степень на порядки выше средней.

- `lr-prepare` — превращает рёберный CSV в бинарный workdir, разбитый на блоки.
- `lr-rank` — итеративно считает ранги по workdir, не загружая граф в память целиком.

LeaderRank — вариант PageRank с ground-узлом вместо параметра затухания: в нём нет
константы α, которую подбирают под данные. Обоснование выбора метрики — в
[REPORT.md](REPORT.md).

Алгоритм и управление памятью реализованы собственным кодом, без внешних
зависимостей в ядре. GoogleTest подтягивается через FetchContent только для тестов;
Python (numpy/scipy/networkx) нужен исключительно для независимого эталона проверки,
на выполнение самой утилиты не влияет.

Обе утилиты многопоточные и детерминированные: результат побайтово одинаков вне
зависимости от числа потоков.

## Быстрый старт

```sh
printf 'from,to\n1,2\n2,3\n3,1\n4,1\n' > edges.csv
build/src/prepare/lr-prepare edges.csv workdir --budget 128M --threads 8
build/src/rank/lr-rank workdir --budget 128M --out ranks.csv --threads 8
cat ranks.csv
```

На выходе — CSV `vertex,rank` с рангами, нормированными к сумме 1.

## Сборка

### В контейнере (рекомендуется, любой хост с podman или docker)

```sh
podman build -t ooc-leaderrank-build containers/
podman run --rm -v "$PWD:/work" ooc-leaderrank-build \
    bash -ec 'cmake -S . -B build -G Ninja && cmake --build build'
```

(`docker` вместо `podman` — команды идентичны.)

Контейнер (`containers/Containerfile`) собирается на базе `ubuntu:22.04` и содержит
clang-18, libc++-18, CMake и Ninja — это гарантирует воспроизводимую сборку на любой
машине без ручной установки тулчейна.

### Нативно (Ubuntu 22.04 с уже установленными clang-18 и libc++-18)

```sh
cmake -S . -B build -G Ninja
cmake --build build
```

Бинарники появятся в `build/src/prepare/lr-prepare` и `build/src/rank/lr-rank`.

Требуется именно clang-18 + libc++: нужна полная поддержка C++23, включая
`std::format`. Целевая платформа — x86-64 Ubuntu 22.04, SSD.

## Формат ввода

CSV, первые две колонки — id вершин `from` и `to` (ребро from→to). Вершины — int32 ≥ 0.
Заголовок (`from,to`) допустим, но не обязателен. Разрешены строки-комментарии
с `#`, пустые строки, CRLF. Граф считается простым: петли (`from == to`)
отбрасываются, дубликаты рёбер схлопываются, счётчики отброшенного пишутся в meta
workdir'а.

## Формат вывода

CSV с заголовком `vertex,rank`. Ранги нормированы (сумма равна 1), строки
отсортированы по возрастанию id вершины, числа — в формате `%.15g`. Вершины, не
встретившиеся ни в одном ребре, в вывод не попадают.

## Использование

```
lr-prepare <edges.csv> <workdir> --budget <размер> [--threads N] [--transpose]

  --budget    обязательный. Бюджет памяти, например 128M, 2G.
  --threads   число рабочих потоков (по умолчанию 1).
  --transpose поменять местами src и dst при чтении
              (ранжировать транспонированный граф).
```

```
lr-rank <workdir> --budget <размер> --out <ranks.csv> [--eps E] [--max-iters M] [--threads N]

  --budget    обязательный. Тот же бюджет памяти, что и на этапе prepare.
  --out       обязательный. Путь выходного CSV.
  --eps       порог сходимости (по умолчанию 1e-9).
  --max-iters потолок числа итераций (по умолчанию 500).
  --threads   число потоков (по умолчанию — threads_planned из meta,
              заданное на этапе prepare).
```

У обеих утилит есть `--help`.

## Проверка

- Юнит-тесты: `ctest --test-dir build` (93 теста).
- Сквозной прогон на golden-случаях: `tests/integration.sh build` (15 случаев,
  prepare → rank → сверка с эталоном, плюс проверка байт-в-байт повторяемости).
- Прогон out-of-core под настоящим лимитом памяти (cgroup):
  `scripts/run_capped.sh <бюджет> <команда>` — на macOS через podman, на Linux
  через systemd-run; печатает `oom_killed` и пиковую память. Это подтверждает,
  что граф не загружается в RAM целиком.

Результаты детерминированы: побайтово одинаковы при повторных запусках и при любом
числе потоков. Корректность сверяется с независимым эталоном на Python
(`scripts/reference_rank.py`), у которого нет ни строки общего кода с C++.

## Многопоточность

Оба этапа (prepare и rank) используют пул потоков (`--threads`) и задействуют все
ядра одного вычислительного узла. Число потоков на результат не влияет: суммы с
плавающей точкой складываются в фиксированном порядке.

## Ограничения

- Id вершин должны быть плотно занумерованы; сильно разреженные id отклоняются
  с советом перенумеровать граф.
- Один сильно скошенный блок рёбер (гипер-узел) должен помещаться в бюджет
  `--budget` на этапе prepare; иначе выводится понятная ошибка с советом увеличить
  бюджет.
- Решение рассчитано на один узел: масштабируется по ядрам, не по машинам.
